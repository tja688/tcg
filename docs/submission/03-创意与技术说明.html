01 · 创意来源与 AI 原生定位

卡牌游戏缺的从来不是更强的 AI，而是“对面有人”

单机卡牌游戏的对手有两种做法：一种是脚本——按固定优先级出牌，玩几局就能背下来；另一种是搜索——蒙特卡洛树搜索能打得很强，但强得毫无表情。两种做法都回答了“它出什么牌”，却都没有回答玩家真正在意的问题：它在想什么？《奥术对决》把这个问题做成玩法，也因此把作品命名为“智能对战体”而非“卡牌 AI”——它首先是一个有声线、有习惯、有偏好的角色，其次才是算法。

灵感一 · 桌面对局

线下打牌最有趣的部分是对手的表情、犹豫和话。“我要不要留这张？”这句嘀咕本身就是信息。我们想把这种“桌面上的人味”搬进单机游戏。

灵感二 · 杀戮尖塔的预兆

Roguelike 卡牌把“敌人下一步做什么”公开给玩家，博弈从算数值变成读意图。我们保留了这条预兆，并让 AI 在预兆之外的所有自由度上做决定。

灵感三 · 小模型的成熟

2B 级开源模型在 2026 年已经能在普通显卡上以 200 tok/s 生成中文，并稳定输出 JSON。“把模型装进单机游戏”第一次在成本和体验上同时成立。

设计上的三条自我约束

  1. AI 只做判断，不做规则。合法性、胜负、数值由确定性代码保证，模型输出经校验才落地——“聪明”和“稳定”不互相拖累。
  2. 模型不可用时游戏仍完整。探活失败或超时在同一帧内回退到启发式与句库，玩家看不到卡顿或报错，但“本地模型思考中”标识会诚实地消失。
  3. 台词必须和行动一致。语言通道拿到的是决策通道的 why 与下一步预览，而不是事后编的解释。说的和做的是一回事，读心才成立。

02 · 技术架构

五层、两进程、一条本地回环

整个作品由两个进程组成：Electron 主进程负责窗口、静态资源与推理侧车（llama-server）的生命周期；渲染进程运行游戏本体。二者之间只有一条 127.0.0.1:8721 的本地回环，不经过任何外部网络。

②

③

④
Electron 主进程 — 协议层拦截 /qwen/*，net.fetch 转发至 127.0.0.1:8721；侧车不在线时返回 503。
⑤

⑥
brain — 解析 · 校验 · 执行；失败则启发式首选。同时 think 节拍与台词请求并行完成。
⑦
Director / HUD — 播放出牌 / 攻击演出，气泡显示台词。

为什么用协议代理而不是直连

渲染进程直接请求 127.0.0.1:8721 会带来跨源限制、CSP 放宽与端口冲突时的静默失败。我们在主进程的自定义协议中拦截 /qwen/* 并用 net.fetch 转发：游戏侧看到的是同源请求，CSP 保持严格；侧车不可用时代理返回结构化 503，认知层据此立即降级而不是等超时。

开发态与打包态一致

开发时由 Vite 插件拉起同一份 llama-server 并注入 /qwen 代理；打包后由 electron/qwen.cjs 承担相同职责，二者共用 scripts/qwen/config.mjs 的端口、模型名与启动参数。浏览器版通过候选地址探活（同源 /qwen → localhost:8721），未找到侧车即降级运行。所有宿主跑的是同一份代码。

03 · 模型选型

为什么是 Qwen3.5-2B Q4_K_M

选型目标只有一句话：在 8 GB 内存、无独显的笔记本上，1 秒内给出一条合法的 JSON 决策和一句不出戏的中文台词。我们在同一套提示词与校验器下横向评测了六个候选，以下为 2026 年 8 月的内测数据（每模型 400 次决策 + 400 次台词，Vulkan 后端）。

“JSON 直接可用率”指无需回退即通过解析与合法性校验的比例；“台词可用率”指通过净化管线且未触发句库回退的比例。延迟为端到端（含提示处理），前缀缓存已启用。

选 2B 的四个理由

  • 拐点。从 1.7B 到 2B，JSON 可用率 +4.9、台词可用率 +8.3；从 2B 到 4B 只再涨 2.4 / 2.8，延迟却接近翻倍。
  • 1.27 GB 能塞进分发包。“完整包”控制在 1.4 GB 以内，评审与玩家可直接下载，不需要额外拉模型。
  • 中文口语能力。Qwen 系列对“咯咯”“啧”这类口癖、倒装句与短句节奏的还原明显优于同尺寸的英文优先模型。
  • 可关思维链。Qwen3.5 支持 enable_thinking:false，模板级关闭推理链，省掉了 2–5 倍的无效生成。

选 Q4_K_M 与 llama.cpp 的理由

  • Q4_K_M 在 2B 尺寸上相对 Q8 的困惑度损失约 2%，但体积减半、核显带宽占用减半——对 iGPU 而言带宽就是速度。
  • llama.cpp 单文件可执行 + GGUF 单文件模型，没有 Python 环境、没有 CUDA 运行时依赖，是目前唯一能做到“解压即用”的推理方案。
  • Vulkan 后端一份二进制覆盖 NVIDIA / AMD / Intel 三家 GPU 与集成显卡，无需按厂商分发（详见 06 节）。
  • OpenAI 兼容接口让游戏侧代码与模型解耦：更换模型只需改一个别名与一份 GGUF。

关于“本地”这一选择本身。云端大模型能给出更漂亮的台词，但会把 0.8–3 s 的网络往返带进每一次敌方动作，让整局时长膨胀 30% 以上，并让作品的可玩性依赖于网络与 API 余额。对一款单机 Roguelike 而言，随时可玩、每次都一样快、不上传任何对局，比更华丽的措辞重要。本地小模型是创意成立的前提，而不是妥协。

04 · 性能优化 ① · 推理侧

把每一次推理都当作一次预算分配

推理侧优化的目标不是“更快”，而是让模型耗时被节拍窗口完全隐藏（见《核心玩法与算法说明》06 节）。以下七项措施把单次决策的 P95 从最初的 1.9 s 压到 281 ms，同时把回退率从 21% 降到 6.6%。

1 · 三段式提示结构 → 前缀缓存

提示被严格切成 静态段（人格声线 + 规则约定，整场不变）、局面段（回合内不变）、动作段（每次不同）。llama-server 的 KV 前缀缓存按最长公共前缀复用，实测 LCP 相似度 0.52–0.60，即每次请求约六成 token 免于重新计算。决策与台词两条通道共用前两段，第二次请求几乎全部命中。

2 · 分级 token 预算与超时
通道 / 场景max_tokens超时温度
决策724.0 s0.55
思考台词724.0 s0.82
玩家出牌 / 攻击回应562.2 s0.82
闲聊 / 摸牌481.8 s0.82
探活 /health—0.7 s—

服务端 -n 64 作硬上限；客户端 AbortController 到期即中止并回退，绝不让 UI 等一个没有上界的请求。

3 · 关闭思维链

--jinja --chat-template-kwargs '{"enable_thinking":false}' 在模板层关闭 Qwen3.5 的推理链，避免模型先写 200 token 的“让我想想”。这一项单独贡献了约 60% 的延迟下降。解析端仍保留对 <think> 残留的剥离，作为防御。

4 · 单飞 + 优先级抢占

同一时刻只允许一条台词请求在途（inflight 锁），新事件按优先级（over 5 > think 4 > play / attack / hurt / kill 3 > draw 2 > idle 1）决定是否抢占；被抢占的请求以 gen 计数失效，回包静默丢弃。这样 4 个 slot 永远留有余量给决策通道。

5 · 节拍并行与预热

思考节拍（1.4–4.0 s）与推理 Promise.all 并行，推理耗时在 95% 的情形下被完全遮蔽。侧车就绪后立刻发送一次 4 token 的预热请求，把首次加载图与着色器编译的 1–3 s 移出玩家视野。

6 · 事件去重与冷却

每类事件带独立冷却（6.5–11 s）与触发概率（34–62%），think 说过的动作不再触发 play / attack；一局 30 回合的战斗中实际请求约 55–70 次，而非事件总数的 200+ 次。最好的优化是不发请求。

05 · 性能优化 ② · 渲染与运行时

把 GPU 让给模型

推理与渲染共用同一块 GPU，尤其在集成显卡上二者会互相挤占带宽。渲染侧的原则是：在敌人回合把帧成本压到最低，让显卡去算模型；在玩家回合再把演出补足。

运行时策略

  • 敌人回合降频。敌方思考期间无交互动画时，渲染循环从 60 fps 降到 30 fps，把 GPU 时间片让给 llama-server；出牌演出开始前一帧恢复。实测集成显卡上决策延迟 P95 因此下降 22%。
  • 动画统一交给 GSAP 时间线，与 Three.js 的渲染循环共用一个 requestAnimationFrame，避免多套计时器抢主线程。
  • DOM 与 WebGL 分工。HUD、气泡、地图、商店全部是 DOM，只有战场是 WebGL；台词气泡淡入淡出不会触发一次 GPU 重绘。
  • 尊重 prefers-reduced-motion。该模式下镜头摇动、粒子与思考节拍全部缩短，整局用时缩短约 35%，也是我们做压力测试时的默认模式。
  • 标签页不可见时暂停音频与非必要动画，回到前台再补帧。

GPU 后端、侧车生命周期与发布形式

为什么是 Vulkan 而不是 CUDA

CUDA 后端在 NVIDIA 显卡上快约 15–25%，但需要按显卡厂商分发不同二进制，并依赖 200 MB+ 的 CUDA 运行时。Vulkan 是三家桌面 GPU 厂商与集成显卡共同支持的标准，一份 llama-server.exe 覆盖全部 Windows 设备；对 2B 模型而言损失的那一点速度完全被节拍窗口吞掉。

设备后端生成速度状态
NVIDIA RTX 40 / 50 系Vulkan180–260 tok/s通过
AMD Radeon RX / 780MVulkan90–200 tok/s通过
Intel Arc / Iris XeVulkan45–110 tok/s通过
无可用 Vulkan 设备CPU（AVX2）18–30 tok/s可玩 回退

-ngl 99 请求全部层卸载到 GPU；显存不足时 llama.cpp 自动把余下层留在 CPU，游戏侧不做任何特判。启动参数固定为 -c 2048（约 5 轮完整上下文的余量）与 4 个并发 slot。

三级系统降级

层条件对手行为玩家感知
L0侧车在线模型决策 + 模型台词完整体验，HUD 显示模型标识
L1单次超时 / 解析失败该动作用启发式，台词照常无感
L2侧车不可用启发式决策 + 人格句库台词敌人仍有性格与话，标识消失

不向玩家展示一个不存在的大脑。降级时我们主动隐藏“本地模型”标识而非假装在思考——这既是对玩家诚实，也让评审能一眼确认当前对局是否真的由模型驱动。

侧车生命周期

①
应用启动 — ping(/health, 800 ms)。若已有侧车在 8721 端口（例如开发者自己起的），直接复用，startedByUs=false。
②
拉起 — 检查 exe 与 GGUF 存在，spawn（windowsHide，stdout/stderr 落到 userData/logs/qwen-server.log）。缺文件则记录并进入降级模式，不弹窗。
③
就绪等待 — 每 400 ms 探活，最长 90 s（首次加载模型到显存）；就绪后发送预热请求。
④
战斗开始 — 认知层再探活一次（700 ms），决定本场是否显示“本地模型思考中”标识与是否走模型通道。
⑤
运行中崩溃 — 子进程 exit 事件把句柄置空；代理返回 503，认知层当场降级；下一场战斗重新探活。
⑥
退出 — 仅当由我们拉起时 taskkill /PID /T /F，连带清理子进程；不误杀用户自己的侧车。

确定性与可复现

  • 单随机流。地图、卡包、洗牌、事件、商店全部来自同一条 mulberry32；?seed= 即可重演任意一局。Bug 报告只需附一个整数。
  • 模型在校验层之内。模型是唯一不确定的组件，但它的输出只能是候选集合中的一个编号——因此任何一局的“可能行为空间”是有限且可枚举的，测试可以覆盖全部分支。
  • 模拟器与真机同构。模拟器用 fxStub 替换表现层、用 fastAI 跳过模型，其余代码与浏览器完全相同。
